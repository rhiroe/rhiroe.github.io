Railsアプリケーションにクエリオブジェクトを導入してみました

複雑なクエリをモデルから切り出すパターン

スコープの肥大化・可読性の低下を解消する

はじめに

Railsを書いていると、複雑な集計をパフォーマンスよく行うために複雑なクエリを組み立てる場面があります。

  • ActiveRecordの scope はクラスメソッドとして自然に使えて便利
  • クエリが複雑になるほど メンテしにくく なる
  • モデルファイルの 見通しが悪くなりがち

→ クエリオブジェクト というパターンを導入して解決しました

導入前の課題感

こういったスコープがモデルに増え続けていた

class Order < ApplicationRecord
  scope :monthly_summary, ->(month:) {
    where(ordered_at: month)
      .joins(:user)
      .where(users: { active: true })
      .group("users.id", "users.name")
      .select("users.id", "users.name",
              "COUNT(orders.id) AS order_count",
              "SUM(orders.total_price) AS total_price")
  }
end

※ これは例なので比較的シンプルですが、実際にはもっと長い生SQLが
あちこちのスコープに埋め込まれており、ひどい有様でした。

  • 何をしているかが一目でわからず、可読性が低い
  • ロジックに名前がつかないため、処理の意図が伝わりにくい
  • モデルファイルがSQL文で埋め尽くされる

クエリオブジェクトとは何か

データの抽出・検索・集計条件を定義した実体

  • Railsの標準機能ではないが、広く使われている設計パターン
  • 複雑なクエリロジックをクラスやモジュールに切り出す
  • クエリを意味ごとに切り分けて 名前をつける ことができる
  • モデルを 汚染しない

なお、再利用性は重要視していません。
異なるテーブルに対して同じSQLを適用したい場面はそうそうないはずであり、
クエリオブジェクトは基本的に特定のモデルに紐づくものと捉えています。

導入にあたってのルール作成

クエリオブジェクトは実装方法や呼び出し方に 自由度が高い ため、チームでのルールが重要です。

ルールなし

  • 統一性のない実装が散乱
  • 呼び出し方がバラバラ
  • サービスクラスの二の舞になりかねない

❌ とりあえず call を持つクラスが乱立

ルールあり

  • コードベースに統一性
  • 一方向の呼び出しフロー
  • 自然にインターフェースが強制される

✓ 予測可能な実装・利用

定めたルール一覧

配置・命名

  1. app/queries/ に配置する
  2. 利用モデルのインナーモジュール
    （例：User::ActiveQuery）
  3. モジュールであること（クラスではない）
  4. モジュール名が Query で終わる

インターフェース

  1. self.call メソッドを定義する
  2. self.call の第一引数はデフォルト値あり
  3. 第二引数以降はキーワード引数
  4. publicクラスメソッドは self.call のみ

呼び出し方（最重要）

9. クエリオブジェクトを直接呼び出さず、ActiveRecordの scope の引数としてのみ使用する

ルール9：scope 経由でのみ呼び出す

❌ NG: 直接呼び出す

Order::MonthlySummaryQuery.call(
  month: Time.current.all_month
)

✓ OK: scope 経由

class Order < ApplicationRecord
  scope :monthly_summary,
        MonthlySummaryQuery
end

Order.monthly_summary(
  month: Time.current.all_month
)

「クエリオブジェクトを使いたければ必ずモデルにスコープを定義する」
という 一方向の流れ が生まれる

暗黙のインターフェース制約： scope に渡す以上、call は当然 ActiveRecord::Relation を返すはずであり、自然とその制約に従った実装になる

実装方法：ディレクトリ構成

app/queries/ というカスタムディレクトリを作成します

app/
└── queries/
    └── order/
        └── monthly_summary_query.rb

ファイル名はスネークケース、モジュール名はキャメルケースで対応：

  • monthly_summary_query.rb → MonthlySummaryQuery
  • order/ → Order の名前空間に配置

Railsのオートロード（Zeitwerk）が app/queries/ を自動的に認識します

実装方法：クエリオブジェクト

class Order < ApplicationRecord
  module MonthlySummaryQuery
    class << self
      def call(scope = Order.all, month:)
        scope
          .then { filter_by_month(_1, month) }
          .then { join_users(_1) }
          .then { aggregate(_1) }
      end

      private

      def filter_by_month(scope, month)
        scope.where(ordered_at: month)
      end

      def join_users(scope)
        scope.joins(:user).where(users: { active: true })
      end

      def aggregate(scope)
        scope.group("users.id", "users.name")
          .select("users.id", "users.name",
                  "COUNT(orders.id) AS order_count",
                  "SUM(orders.total_price) AS total_price")
      end
    end
  end
end

実装のポイント

  • モデルの名前空間の中に定義
    どのモデルに関するクエリかが明確になる
  • call を入口にする
    RubyのCallableオブジェクトの慣習。scopeに渡しやすくなる
  • scope を引数に取る
    呼び出し元のスコープと組み合わせられる柔軟な設計
  • 複雑なクエリをprivateメソッドに分割
    それぞれに名前がつき、処理の意図が伝わりやすくなる
    call を読むだけで処理の流れが把握できるのが理想

呼び出し方とテスト

class Order < ApplicationRecord
  scope :monthly_summary, MonthlySummaryQuery
end

# 使う側はいつものスコープと同じ感覚
Order.monthly_summary(month: Time.current.all_month)

クエリロジックが独立したモジュールになることで単体テストも書きやすい

RSpec.describe Order::MonthlySummaryQuery do
  describe ".call" do
    it "指定月のアクティブユーザーの注文を集計する" do
      active_user   = create(:user, active: true)
      inactive_user = create(:user, active: false)
      create(:order, user: active_user,   ordered_at: month + 1.day)
      create(:order, user: inactive_user, ordered_at: month + 1.day)

      result = described_class.call(month: month)

      expect(result.map(&:user_id)).to contain_exactly(active_user.id)
    end
  end
end

なぜこのルールなのか

モジュールを強制する（ルール3）

クエリオブジェクトはステートレスであるべき。インスタンスを生成する必要がないことを明示するためにクラスではなくモジュールで定義します。

scope 経由での受け渡しを強制する（ルール9）

  • 呼び出し方を統一できる
  • 「クエリオブジェクトを使いたければ必ずモデルにスコープを定義する」という一方向の流れが生まれる
  • scope に渡すという制約が、インターフェース（ルール5〜8）をある程度自然に強制する効果もある

RuboCopのCustomCopで強制する

ルールを決めただけでは形骸化しがちです。これらのルールをCustomCopとして実装し、CIで自動検知できるようにしました。

ルール1〜9すべてをCopで検知しています
配置・命名・インターフェース・呼び出し方、それぞれに対応するオフェンスを定義

CustomCopの実装は AIにルールを伝えて生成 させました。
「どんな違反を検知したいか」を説明するだけで動くコードが得られるため、導入のハードルはほぼありません。

まとめ

  1. 複雑なクエリをモデルのスコープに直書きすると可読性・保守性が低下する
  2. クエリオブジェクトとしてモジュールに切り出すことで解決できる
  3. 自由度が高いぶん、チームでのルールが重要
  4. scope 経由の呼び出しを強制することで一方向の流れが生まれる
  5. CustomCopでルールをCIに組み込み、形骸化を防ぐ

クエリロジックの責務を切り出し、モデルの肥大化を抑える
クエリに名前をつけて、単体テストも書きやすく
