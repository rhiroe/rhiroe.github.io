RSpecで環境変数をテストする

with_envヘルパーのすすめ

既存のallow(ENV)の問題を解決する新しい方法

なぜ環境変数を使うのか

  • 設定値へのアクセス権限を厳密に管理する必要がある
  • APIキー、DB接続情報など機密性の高い設定が多い

Rails credentialsの課題

  • master.keyを共有する必要がある
  • 開発メンバー全員が本番の機密情報にアクセスできてしまう

✓ AWS Parameter Store + IAM

  • アクセス権限をIAMポリシーで細かく制御
  • 「本番環境のみ」「開発環境のみ」といった制御が可能

既存の方法：allow(ENV)によるスタブ

RSpecの標準機能で環境変数をスタブ

RSpec.describe SomeApiClient do
  it 'uses API key from ENV' do
    allow(ENV).to receive(:[]).and_call_original
    allow(ENV).to receive(:[]).with('API_KEY').and_return('test_key')

    client = SomeApiClient.new
    expect(client.api_key).to eq 'test_key'
  end
end

and_call_originalと組み合わせて使う必要がある

注意点1: 実装の詳細に依存する

ENVにアクセスするメソッドは複数ある

ENV['API_KEY']           # []
ENV.fetch('API_KEY')     # fetch

⚠️ []をスタブしても、コードがfetchを使っていると動かない

allow(ENV).to receive(:[]).with('API_KEY').and_return('test_key')

api_key = ENV.fetch('API_KEY')  # => nil

実装を変更しただけでテストが壊れてしまう

注意点2: and_call_originalが必要

and_call_originalを書かないと...

allow(ENV).to receive(:[]).with('API_KEY').and_return('test_key')

ENV['DATABASE_URL']  # => nil

⚠️ スタブしていない他のキーがnilになり、予期しない場所でテストが落ちる

正しい書き方：

allow(ENV).to receive(:[]).and_call_original
allow(ENV).to receive(:[]).with('API_KEY').and_return('test_key')

新たな方法：with_envヘルパー

✓ 注意点を見落とすリスクを根本的に排除

RSpec.describe SomeApiClient do
  it 'uses API key from ENV' do
    with_env('API_KEY' => 'test_key') do
      client = SomeApiClient.new
      expect(client.api_key).to eq 'test_key'
    end
  end
end

実際のENVオブジェクトを一時的に書き換える

with_envヘルパーの実装

module EnvHelpers
  def with_env(hash)
    original = ENV.to_hash
    hash.each { |k, v| ENV[k] = v }

    begin
      yield
    ensure
      ENV.replace(original)
    end
  end
end

シンプルな実装で、ensureブロックにより確実にクリーンアップされる

既存の方法 vs 新しい方法

allow(ENV) with_env
実装の詳細への依存 []か fetch かを意識する必要がある 意識する必要がない
暗黙知の要求 and_call_original を知っている必要がある 特に必要ない
複数メソッドへの対応 [] と fetch を両方スタブする必要がある 何もしなくても動く

カスタムコップで統一を促す

チーム全体で新しい方法を使うようにする

class AvoidAllowEnv < RuboCop::Cop::RSpec::Base
  MSG = '`allow(ENV)` の代わりに `with_env` を使用してください'

  def_node_matcher :allow_env?, <<~PATTERN
    (send nil? :allow (const nil? :ENV))
  PATTERN

  def on_send(node)
    add_offense(node) if allow_env?(node)
  end
end

既存のコードベースからallow(ENV)を発見して段階的に移行

なぜwith_envに統一するのか

allow(ENV)の正しい使い方を強制

  • 順序のチェックが必要
  • 複数メソッドのチェックが必要
  • ASTの解析が複雑

❌ 実装が困難

with_envに統一

  • リスクを根本的に排除
  • シンプルな検知
  • 段階的な移行が可能

✓ 確実で効果的

まとめ

  1. allow(ENV)には注意点があり、見落とすとテストが不安定になる
  2. with_envヘルパーという新しい方法を用意した
  3. 実装の詳細に依存せず、暗黙知も不要
  4. カスタムコップで統一を促進

環境変数のテストは地味だが重要
